# trt-rs Full Audit — 2026-06-12

Five-agent audit (architecture/VPI, API ergonomics, CUDA kernels, unsafe/FFI, shipping) 
with adversarial verification of all bug-class findings. 10 agents total.

## Unsafe / FFI Soundness

The FFI layer itself (trt-sys, logger shim, nvbuf-sys) is solid: catch_unwind plus a C++ try/catch guard the logger callback, error storage is thread-local, the Arc chain (Logger->Runtime->Engine->Session) enforces destruction order, and DeviceBuffer frees are stream-ordered via cudarc 0.17's free_async, so happy-path frame execution is sound. The real soundness debt is concentrated in error-path teardown and in raw device pointers whose validity is enforced only by convention: when any stage's enqueue fails mid-frame, Pipeline::next returns without syncing the stream or running finalize, and the next frame (or a drop) then destroys the still-in-flight NVMM external-memory import and texture object — a demonstrable GPU use-after-free reachable with the exact continue-on-error loop both examples use. Secondarily, TRTensorMap/run_device_inputs_on_device pointers and XFeatPostprocStage's stored desc_ptr have no type-level tie to the owning Session, so plain safe Rust (dropping or re-running the producer stage before finalize) dangles them. Remaining issues are minor (alignment-UB-by-spec in OutputTensor::as_f32, context leak on constructor failure, stale error text).

### Findings

#### [CRITICAL] Mid-frame error path frees NVMM import and destroys texture object while GPU work is still in flight
`crates/trt/src/pipeline.rs:265`

Pipeline::next returns early on any enqueue error (crates/trt/src/pipeline.rs:265, also the record_event error at :268-271) WITHOUT syncing the stream and WITHOUT calling finalize. Both examples treat this as recoverable and loop again (examples/rtsp_xfeat/src/main.rs:142, examples/rtsp_yolo/src/main.rs:65). Triggering sequence: frame N — NvmmPreprocessStage::enqueue succeeds (letterbox kernel enqueued async, CudaMemory stored in _pending, TextureGuard stored in Preprocessor._pending); a downstream stage's enqueue then fails (e.g. btrt_context_enqueue_v3 returns nonzero); Pipeline::next returns Some(Err) with the kernel possibly still running. Frame N+1 — NvmmPreprocessStage::enqueue (crates/trt-gst/src/lib.rs:315) executes `self._pending = Some(mem)`, dropping frame N's CudaMemory -> nvbuf_cuda_release -> cudaFree + cudaDestroyExternalMemory (crates/nvbuf-sys/src/nvbuf_shim.cpp:118-121) while frame N's kernel may still be reading that memory, and while the texture object referencing it still exists; then Preprocessor::enqueue (crates/trt-preproc/src/lib.rs:262) drops the old TextureGuard -> cudaDestroyTextureObject mid-flight. Both shims document 'call only after stream sync' — the precondition is violated by safe code under the documented usage pattern. Same hazard if the user instead drops the Pipeline after the error: Session::drop (crates/trt/src/session.rs:321-327) deletes the IExecutionContext with enqueueV3 work pending, and CudaMemory/TextureGuard drop unsynced.

**Recommendation:** In Pipeline::next, on any enqueue/record_event error: sync the stream (best-effort) before returning the error, and consider still invoking finalize-as-cleanup. Defense in depth: NvmmPreprocessStage::enqueue and Preprocessor::enqueue should sync the stream before overwriting a still-Some _pending; CudaMemory::drop and TextureGuard::drop could each carry the Arc<CudaStream> and sync if a 'pending' flag is set.

#### [MAJOR] TRTensorMap / run_device_inputs_on_device raw output pointers have no lifetime tie to the owning Session
`crates/trt/src/session.rs:223`

run_device_inputs_on_device (crates/trt/src/session.rs:223-239) returns raw *mut c_void aliasing Session-owned DeviceBuffers; resize_output_buffers (session.rs:304-318) drops and reallocates those buffers on the NEXT run_* call whenever the resolved output shape changes, and Session::drop frees them. TRTensorMap (crates/trt/src/pipeline.rs:74-83) is a plain Send struct with a pub HashMap of these pointers and no back-reference to the session; XFeatPostprocStage stores one of them (desc_ptr) from enqueue to finalize (crates/trt-xfeat/src/model.rs:202, consumed at :207). All of the following are plain safe Rust and dangle the pointer: (a) dropping the producer TrtInferStage before the consumer's finalize when stages are composed manually instead of via Chain; (b) calling the producer's enqueue twice (dynamic shapes) before the consumer's finalize; (c) cloning pointers out of the pub HashMap and using them next frame. The only mitigations are conventions: the Pipeline call order and cudarc's stream-ordered free (which protects in-flight GPU reads but not newly launched kernels on the stale address). The 'SAFETY: desc_ptr is a stable device address' comments at model.rs:168 and :243 are insufficient as stated — stability holds only until the next session run with a shape change or session drop.

**Recommendation:** Make TRTensorMap hold something that keeps the buffers alive and detects invalidation: e.g. Arc<DeviceBuffer> per output plus a generation counter checked in finalize, or borrow the map with a lifetime tied to &Session until the next &mut call. Important for the VPI-like operator-library direction where third parties will write stages against this contract.

#### [MAJOR] Dropping the GStreamer Sample early (error path) lets the decoder pool overwrite an NVMM buffer still being read by CUDA
`crates/trt-gst/src/lib.rs:55`

NvmmFrame's _keep_alive Box (crates/trt-gst/src/lib.rs:55-63) holds the Sample; in Pipeline::next the frame is a local dropped at end of scope, so on the same early-error return (pipeline.rs:265) the Sample is released back to the nvv4l2decoder buffer pool while the letterbox kernel may still be reading the imported memory. Because nvbuf_cuda_import dup()s the fd (nvbuf_shim.cpp:83) and cudaImportExternalMemory holds a dmabuf reference, the allocation itself stays mapped — so this is not a host UAF, but the decoder can recycle and rewrite the surface concurrently with the in-flight kernel read (GPU data race, corrupted tensors on subsequent recovered frames). Happy path is correct: frame drops after sync+finalize.

**Recommendation:** Covered by the same fix as the critical finding (sync stream on Pipeline error paths before the frame drops). Alternatively move the NvmmFrame into the preproc stage's _pending alongside CudaMemory so its release is always finalize-ordered.

#### [MINOR] OutputTensor::as_f32 casts a Vec<u8> base pointer to &[f32] without alignment check
`crates/trt/src/session.rs:27`

crates/trt/src/session.rs:24-32: `std::slice::from_raw_parts(self.data.as_ptr() as *const f32, ...)` on a Vec<u8> whose guaranteed alignment is 1. from_raw_parts with a misaligned pointer is immediate UB per its documented contract. In practice the global allocator returns >=8-byte-aligned blocks for these sizes, so it never misfires today, but it is UB-by-spec and would break under a custom allocator or sub-slicing. trt-yolo consumes this on every frame (crates/trt-yolo/src/lib.rs:280).

**Recommendation:** Use bytemuck::try_cast_slice (with an alignment-checked error) or read via chunks_exact(4).map(f32::from_le_bytes); alternatively allocate output staging as Vec<f32> and view as bytes for the D2H copy.

#### [MINOR] Session constructors leak the IExecutionContext if buffer allocation fails
`crates/trt/src/session.rs:92`

In Session::with_stream (crates/trt/src/session.rs:92-121) and Session::new (:130-157) the btrt_context_create result is held as a raw pointer; if DeviceBuffer::alloc_with_stream fails mid-loop the function returns Err without calling btrt_context_destroy — the C++ ShimContext and TRT context leak. Leak only, not UB.

**Recommendation:** Wrap the raw ctx in a small guard (or construct Self before allocating buffers) so Drop runs on every early-exit path.

#### [INFO] btrt_last_error returns stale/unrelated text for enqueue/setTensorAddress/setInputShape failures
`crates/trt-sys/src/trt_bridge.cpp:252`

g_last_error (crates/trt-sys/src/logger_shim.cpp:17) is set only by the create/deserialize paths and cleared only there (trt_bridge.cpp:28-30); btrt_context_enqueue_v3, btrt_context_set_tensor_address and btrt_context_set_input_shape (trt_bridge.cpp:212-257) return -1 without setting it, so TrtError::Trt(last_trt_error()) at e.g. crates/trt/src/session.rs:252 can attach a stale message from an earlier call on the same thread (TRT's real diagnostics go through the logger on a different thread). Thread-locality itself is correctly handled — Rust reads on the same thread that made the failing call. Diagnostics quality, not soundness.

**Recommendation:** set_error in the failing context functions (the actionable detail will be in the logger; at minimum store the function name), and clear_error at the top of each fallible call.

#### [INFO] Logger callback and appsink callbacks verified sound
`crates/trt/src/logger.rs:22`

Q4/Q5 confirmations: the TRT logger path is double-guarded — C++ try/catch around the callback under a mutex (crates/trt-sys/src/logger_shim.cpp:39-43) and Rust catch_unwind around the log macros (crates/trt/src/logger.rs:29-36); CStr handling outside catch_unwind cannot panic. The NVMM appsink callback (crates/trt-gst/src/lib.rs:171-209) extracts fd/pitch/size before dropping the buffer map, validates layout==PITCH, and try_send failures just drop the Sample on the GStreamer thread — benign frame drops, no UB. The CPU-snapshot path's Arc<Mutex<Option<...>>> overwrite (:214-239) is plain safe sharing. Also verified: cudarc 0.17 CudaSlice::drop is stream-ordered (free_async on the owning stream, core.rs:560-578), which makes Session::resize_output_buffers safe with respect to in-flight same-stream work, and the 'async' D2H copies into pageable Vecs (session.rs enqueue_and_collect, trt-yolo lib.rs:379-385) are synchronous by CUDA pageable-memcpy semantics, so the host buffers are never read before the data lands.

**Recommendation:** No action needed; consider documenting the pageable-memcpy reliance in YoloInferStage::enqueue, since switching output_cpu to pinned memory would silently change it to a genuinely async copy.

## CUDA Kernels

All six CUDA kernels were audited (letterbox in trt-preproc; score_nms, sample_descs, l2_norm, match_rows, match_cols in trt-xfeat) plus their launch sites and buffer lifecycles. No critical correctness bugs: every uninitialized stream.alloc buffer is fully overwritten by its kernel before being read, all reductions are properly synchronized, bilinear corner clamping in sample_descs is safe, and int32 indexing has ample headroom at these resolutions. The real costs are performance-shaped: the mutual-NN match kernels are barrier-dominated (one 64-MAC dot product per 2 barriers and 5 shuffles), estimated ~10-15 ms combined at K=4096 — slower than the backbone — and the top-K step copies the full 3.7 MB score map D2H with a 921k-element CPU scan every frame (~1.5-3 ms in finalize). Three small but genuine accuracy issues exist in the sampling conventions: a missing half-pixel-center in the letterbox mapping, black-border blending on right/bottom content edges, and NMS plateau ties producing duplicate keypoints. Structurally, the kernels have no unit tests against CPU references (despite a ready CPU matching oracle in the same file) and triplicate the warp-reduction boilerplate, which matters for the stated goal of a clean operator library.

### Findings

#### [MAJOR] Brute-force mutual-NN match kernels are barrier-dominated; estimated ~10-15 ms combined at K=4096
`crates/trt-xfeat/src/postprocess.rs:130-202,515-531`

xfeat_match_rows/xfeat_match_cols use one 64-thread block (2 warps) per query with a serial loop over all candidates. Each inner iteration computes ONE 64-MAC dot product using 1 FMA per thread, then 5 __shfl_down_sync, 2 shared stores, and 2 __syncthreads. That is ~19 warp-instructions per warp per iteration for 64 useful FLOPs (~3% arithmetic efficiency). At N0=N1=4096 (the top_k used in examples/rtsp_xfeat/src/main.rs:107): 4096 blocks x 4096 iterations x 2 warps ~= 640M warp-instructions per kernel; at ~4 warp-instr/cycle/SM x 16 SMs x 1.3 GHz this is roughly 8 ms per kernel, ~15 ms for the pair — larger than the ~10 ms backbone itself. SM87 also caps at 16 blocks/SM, so 2-warp blocks leave occupancy at 32/48 warps. Note: at the moment match_mutual_nn_gpu is only exercised in pair-matching use, not in the rtsp_xfeat per-frame loop, so it does not affect that demo's frame time — but it is the advertised GPU matching path.

**Recommendation:** Measure first with the existing CUDA-event timing, then restructure: either (a) cuBLAS SGEMM D0*D1^T (4096x64x4096 = 2.1 GFLOP, sub-ms on Orin) followed by trivial row/col argmax kernels (67 MB sim matrix read ~0.7 ms), or (b) a fused tiled kernel: one thread per query holding its 64-float descriptor in registers, looping over D1 tiles staged in shared memory, doing 64 FMAs per candidate with no shuffles/barriers in the inner loop. Either gets the pair under ~2 ms. Also write match_out from match_cols into the row kernel's consumer order or keep as-is — correctness is fine, only the shape is wrong.

#### [MAJOR] Top-K step copies the full HxW score map D2H and scans it on CPU every frame (~1.5-3 ms in finalize)
`crates/trt-xfeat/src/postprocess.rs:314-334 (also 417-449)`

process_topk_sample does memcpy_dtov of the entire score map (1280x736 = 921k floats = 3.7 MB) then a CPU filter/collect into Vec<(f32,u32)>, select_nth_unstable, and sort, every frame. On Jetson the D2H alone is ~0.5-1 ms and the 921k-element scan + allocation another ~1-2 ms, all on the finalize critical path of the frame loop (single-threaded pipeline.next()). The NMS kernel already zeroes non-survivors, so typically only a few thousand of 921k elements are nonzero — almost all of the copy and scan is wasted.

**Recommendation:** Add a GPU stream-compaction pass: an atomicAdd counter kernel that appends (score, idx) for score>0 survivors into a compact buffer, then D2H only count*8 bytes (tens of KB) and run the existing CPU select_nth on that. Alternatively cap survivors with a GPU top-K (e.g., per-block heaps or CUB DeviceRadixSort on ~5k items). This also removes the per-frame 3.7 MB Vec allocation in memcpy_dtov.

#### [MINOR] Letterbox blends right/bottom content edges toward black (cudaAddressModeBorder + unclamped sample coordinate)
`crates/trt-preproc/src/preproc_helpers.cpp:39-40, crates/trt-preproc/src/lib.rs:90-99`

The texture uses cudaAddressModeBorder (out-of-bounds returns {0,0,0,0}) while the kernel guards only sx/sy in [0, src_w/src_h). For sx in (src_w-1, src_w) the hardware bilinear tap at sx+0.5 > src_w-0.5 blends the last valid pixel with the black border — up to 50% black on the last output column/row of content, immediately adjacent to grey-114 padding. For YOLO this is cosmetic; for XFeat it manufactures a strong artificial gradient along two image edges that the 5x5 NMS can promote to spurious keypoints (heatmap edge responses).

**Recommendation:** Switch addressMode to cudaAddressModeClamp (edge replicate, matching cv2.copyMakeBorder/resize behavior); the kernel's own range guard already produces the grey fill outside content so border mode contributes nothing useful.

#### [MINOR] Letterbox resampling omits the half-pixel-center convention; inconsistent with xfeat_sample_descs and cv2.resize
`crates/trt-preproc/src/lib.rs:84-85`

The kernel maps sx = (ox - pad_x)/scale, then samples at sx+0.5. The standard align_corners=False / cv2.resize mapping is sx = (ox + 0.5 - pad_x)/scale - 0.5. The difference is a constant shift of 0.5/scale - 0.5 source pixels (~0.25 px at scale 2/3, growing for stronger downscales). xfeat_sample_descs (postprocess.rs:79-80) correctly uses the half-pixel convention, so within-model keypoint->descriptor sampling is self-consistent, but every keypoint coordinate carries a systematic sub-pixel bias relative to the original camera image — relevant once keypoints feed geometry (pose, triangulation), and a train/inference mismatch vs the cv2-preprocessed XFeat training data.

**Recommendation:** Change to: float sx = ((float)ox + 0.5f - pad_x) / scale - 0.5f; (same for sy). The +0.5f at the tex2D call site stays. One-line fix, verify against a CPU cv2.resize reference.

#### [MINOR] NMS strict '>' lets equal-score plateaus survive as duplicate adjacent keypoints
`crates/trt-xfeat/src/postprocess.rs:47-57 (kernel string)`

A neighbour suppresses the centre only if strictly greater. Two (or more) adjacent pixels with bitwise-equal heatmap values all survive and become duplicate keypoints ~1-2 px apart. With the FP16 backbone the heatmap is quantized to fp16 values, making exact ties on peaks plausible. This matches the PyTorch reference (heat == maxpool(heat)) so it is a faithful port, not a divergence — but duplicates waste top-K slots and create ambiguous mutual-NN matches.

**Recommendation:** Break ties lexicographically: suppress if (n > h) || (n == h && (ny*W+nx) < idx). One extra comparison, deterministic, removes all duplicates.

#### [INFO] xfeat_sample_descs interpolation deviates slightly from the XFeat reference interpolator
`crates/trt-xfeat/src/postprocess.rs:77-96`

The kernel uses bilinear with dx = (px+0.5)/W*Wd - 0.5. The verlab reference InterpolateSparse2d normalizes by (W-1, H-1) with grid_sample(align_corners=False), giving dx = px*Wd/(W-1) - 0.5, and (in detectAndCompute) uses bicubic mode. The coordinate difference is <= 1/16 of a descriptor cell (~0.5 full-res px) and bilinear-vs-bicubic changes descriptor values slightly; after L2-norm and mutual-NN the practical impact is small. The corner clamping itself is correct (asymmetric clamp still yields weights summing to 1 with coincident taps), and there is no OOB for NMS-grid keypoints.

**Recommendation:** If exact parity with the Python reference matters for matching quality benchmarks, mirror the reference's (W-1,H-1) normalization; otherwise document the chosen convention. Verify reference mode (bilinear vs bicubic) for the descriptor path before changing.

#### [INFO] No GPU-kernel unit tests despite an existing CPU oracle; kernel sources share no helpers
`crates/trt-xfeat/src/postprocess.rs:23-203, crates/trt-preproc/src/lib.rs:70-104`

All 6 kernels live as raw strings with zero tests (only trt-yolo has CPU tests, crates/trt-yolo/src/lib.rs:402+). The CPU match_mutual_nn (postprocess.rs:555-596) is a ready-made oracle for the match kernels but nothing compares them. The 2-warp shuffle+shared reduction is copy-pasted three times (l2_norm, match_rows, match_cols); descriptor dim 64 is hard-coded in kernel bodies AND independently in LaunchConfig block_dim (postprocess.rs:354,464,515,524) with no shared constant — a silent desync hazard for the stated goal of a VPI-like operator library where new operators are added often.

**Recommendation:** Add #[cfg(test)] GPU tests (they run fine on the Jetson dev box): match kernels vs match_mutual_nn on random normalized descriptors; score_nms, l2_norm, sample_descs, and letterbox vs naive Rust references. Factor a shared kernel-prelude string (warp reduce, bilinear taps, DESC_DIM constant) concatenated into each nvrtc compile, and one Rust const DESC_DIM: u32 = 64 used for block_dim. Consider fusing l2_norm into the tail of sample_descs (saves a launch; trivial since both are K x 64). The k>=K guard in l2_norm (line 109) is dead code given exact grid sizing.

#### [INFO] xfeat_score_nms and letterbox kernels are correctly sized and not worth tiling
`crates/trt-xfeat/src/postprocess.rs:31-61, crates/trt-preproc/src/lib.rs:70-104`

Verified non-issues, recorded so other audits don't re-flag: score_nms writes score_out on every control path, so the uninitialized stream.alloc score buffers (model.rs:67,185,273) are fully overwritten before the D2H read; window clamping via continue is bound-safe; the threshold early-exit means most of the 921k pixels cost 1 load + 1 store (~8 MB traffic, well under 0.2 ms), and __ldg gives the survivors' 25-tap windows good read-only-cache reuse — a shared-memory tile would not pay off. **Recommendation:** No action. Keep optimization attention on the match kernels and the top-K D2H path.

## Architecture (VPI-for-NN alignment)

trt-rs already implements the load-bearing half of a VPI-style runtime: Stage = algorithm+payload (pre-allocated buffers reused per frame), one shared Arc<CudaStream> = VPI stream, two-phase enqueue/finalize = submit/sync, CUDA-event GPU timing, and a genuinely zero-copy NVMM->CUDA ingest path. What is missing is the other half: there is no buffer/image model (six coexisting representations, and the inter-stage TRTensorMap degrades to shapeless raw c_void pointers), no backend concept (letterbox/resize exists three times — CPU in trt-yolo, CUDA in trt-preproc, VIC hidden in a GStreamer caps string — with manually-coupled coordinate params), no events as a public sync primitive, and the typed linear Chain cannot express the multi-input/DAG topologies the stated direction requires (descriptor matching, the flagship two-input op, already lives outside the Stage system as XFeatPostproc::match_mutual_nn_gpu, and visualization fan-out is hacked via an Arc<Mutex> side channel). The Stage contract itself is sound in shape but unenforced: XFeat stages sync inside enqueue, breaking the one-sync-per-frame invariant the Pipeline is built on. Target architecture: (1) one Tensor type (shape/strides/dtype/MemKind{Device,Unified,Imported}) with an Image view (pitch/format) replacing TRTensor/DeviceFrame/NvmmFrame-as-data/CudaSlice/raw ptrs, and TensorMap carrying typed views; (2) an Operator trait with GAT input (tuples for multi-input), an ExecCtx (stream+events+frame metadata) threaded through enqueue/finalize, and finalize returning Result<&Output> instead of a panicking output(); (3) Join/Fork combinators over the existing typed Chain for the common DAG shapes; (4) a Backend enum at operator construction (Cuda(stream)/Vic/Cpu, DLA as an engine-build/session config seam) rather than a full dispatch layer; (5) a ModelSession helper so a new NN operator is ~20 lines: bind inputs, enqueue, name outputs, optional postproc payload.

### Findings

#### [MAJOR] TRTensorMap erases shape and dtype at the model boundary — inter-stage currency is HashMap<String, *const c_void>
`/home/nvidia/trt-rs/crates/trt/src/pipeline.rs:74`

TrtInferStage's output (the type every postproc stage consumes) is a map of bare device pointers with no shape, dtype, or size. Downstream stages must re-acquire dimensions out of band: XFeatPostprocStage::new takes h/w that the doc comment says 'must match the shapes the TRT engine was built with' (crates/trt-xfeat/src/model.rs:176-187), and YoloInferStage must query the Session it owns for output_byte_len/output_shape (crates/trt-yolo/src/lib.rs:362-380). The Session already knows resolved shapes (session.rs:292-302) but throws them away in run_device_inputs_on_device. This is the single worst mismatch with a VPI-like model, where buffers always carry their format.

**Recommendation:** Replace TRTensorMap with HashMap<String, TensorView> where TensorView = {ptr, shape: SmallVec<i64>, dtype, byte_len}, populated from the Session's resolved shapes after enqueue. Postproc stages then derive h/w/k from the view instead of constructor params, eliminating the manual coupling.

#### [MAJOR] Stage contract (enqueue = GPU-only, one sync per frame) is documented but not enforced — XFeat path actually syncs 2-3x per frame
`/home/nvidia/trt-rs/crates/trt-xfeat/src/model.rs:127`

XFeatInferStage::enqueue calls session.stream().sync() inside enqueue (model.rs:126-127), and XFeatPostproc::process_topk_sample does an internal stream.synchronize() (postprocess.rs:368) called from finalize. The Pipeline's gpu_ms event bracket (pipeline.rs:260-280) and the 'one cudaStreamSynchronize per frame' invariant in CLAUDE.md are silently violated. Worse, Chain::enqueue feeds b.enqueue(a.output()) before any sync (pipeline.rs:54-57), which is only correct if b's enqueue touches device pointers exclusively — a stage that reads CPU-visible data in enqueue compiles fine and reads stale memory. The contract is purely conventional.

**Recommendation:** Thread an ExecCtx through enqueue/finalize that owns the stream and is the only way to launch/copy; make sync a private ExecCtx capability not reachable from enqueue. For algorithms that genuinely need a mid-frame CPU step (XFeat top-K), model it as two stages or an explicit 'host step' the pipeline schedules between syncs, so the timing model stays truthful.

#### [MAJOR] Single-input Stage + linear Chain cannot express the library's own flagship multi-input op (descriptor matching) or any fan-out
`/home/nvidia/trt-rs/crates/trt/src/pipeline.rs:29-65`

Stage has exactly one Input and Chain is strictly A->B (pipeline.rs:41-65); Pipeline supports one Source. Two-image matching — already implemented as GPU kernels (match_rows/match_cols, XFeatPostproc::match_mutual_nn_gpu at postprocess.rs:492) — cannot be a Stage and is invoked manually outside the pipeline. Fan-out is also impossible: the visualization branch is implemented as a GStreamer tee plus an Arc<Mutex<Option<(Vec<u8>,u32,u32)>>> side channel on RtspSource (crates/trt-gst/src/lib.rs:107, 211-239, 257), i.e. a second data path that bypasses the pipeline entirely. For the stated direction (composable NN operators: detect+track, stereo, multi-camera), this is the main structural blocker.

**Recommendation:** Evolve Stage to Operator with a GAT input (type Input<'a>) so tuples like (&'a XFeatResult, &'a XFeatResult) work, and add typed combinators: Join<A,B> (Output=(A::Output,B::Output)), Fork (clone/borrow output to N consumers), and a two-source Pipeline variant. Keep the compile-time-typed Chain for the linear fast path; only add a runtime DAG if combinators prove insufficient.

#### [MAJOR] No backend concept — letterbox/resize implemented three times (CPU, CUDA, VIC) with three APIs and manually-synchronized parameters
`/home/nvidia/trt-rs/crates/trt-gst/src/lib.rs:127-141`

The same logical operation exists as: CPU letterbox_rgb_to_chw + LetterboxInfo (crates/trt-yolo/src/lib.rs:28-99), the CUDA texture kernel with its own scale/pad_x/pad_y (crates/trt-preproc/src/lib.rs:143-145), and VIC resize expressible only as a width/height caps string at source construction (trt-gst lib.rs:138-141) — not composable mid-pipeline. YoloInferStage::new takes an lb_info that 'must match the source -> model dimension mapping used by the upstream NvmmPreprocessStage' (trt-yolo lib.rs:319-321): the coordinate un-mapping is coupled by convention across two crates. This is exactly the problem VPI's backend concept solves (one algorithm, N implementations, uniform parameters).

**Recommendation:** Introduce a single Letterbox operator with Backend::{Cuda(stream), Vic, Cpu} chosen at construction, owning one canonical LetterboxInfo that downstream decode stages obtain from the operator (or that travels as frame metadata) instead of being re-derived. VIC backend wraps an nvvidconv/NvBufSurfTransform payload so it works mid-pipeline, not only at the source.

#### [MAJOR] Fragmented buffer/tensor model: six coexisting representations with no common image/tensor type
`/home/nvidia/trt-rs/crates/trt/src/tensor.rs:24`

Data crosses stage boundaries as: TRTensor (shape Vec<usize>, no strides, no memory-kind, owns a stream Arc), DeviceBuffer (untyped bytes, buffer.rs:15), CudaSlice<f32> (xfeat score_dev, model.rs:161), raw *const c_void in TRTensorMap, DeviceFrame {ptr,pitch} (trt-preproc lib.rs:60), NvmmFrame {fd,pitch,size} (trt-gst lib.rs:55), plus host-side OutputTensor (session.rs:15). There are also two stream wrappers (trt::buffer::Stream vs Arc<CudaStream>) converted via Stream::from_cuda_stream on every TRTensor::as_mut_ptr call (tensor.rs:58-61) and per pipeline sync (pipeline.rs:274). TRTensor::as_mut_ptr from &self plus blanket 'unsafe impl Send' on five types puts all aliasing/lifetime safety on convention. Unified memory (Jetson's distinguishing feature) is not represented at all.

**Recommendation:** Converge on one Tensor {storage, shape, strides, dtype, mem: MemKind{Device, Unified, Imported(handle)}} plus a thin Image view (pitch-linear, format) for pre-tensor frames; NvmmFrame stays as the source handle but imports into Tensor/Image with MemKind::Imported. Delete the duplicate Stream wrapper and standardize on one stream type.

#### [MINOR] Session conflates binding, buffer ownership, and sync policy across three run_* variants with duplicated constructors
`/home/nvidia/trt-rs/crates/trt/src/session.rs:91-157`

Session::new and Session::with_stream duplicate ~40 lines of buffer-allocation logic verbatim. Three entry points (run, run_device_inputs, run_device_inputs_on_device) each embed a different copy/sync policy — enqueue_and_collect performs its own stream.sync() (session.rs:281), so calling run() inside a pipeline would break the single-sync model. The Session is simultaneously the VPI 'payload' (pre-allocated buffers) and an ad hoc executor.

**Recommendation:** Reduce Session to payload + enqueue: new(engine, stream) (single constructor; standalone case passes a fresh stream), bind(name, &Tensor), enqueue(ctx), outputs() -> typed views. Host-copy convenience (current run()) becomes a helper built on top, not a peer API.

#### [MINOR] Per-frame NVMM cudaImportExternalMemory and texture-object create/destroy — missing payload-style caching
`/home/nvidia/trt-rs/crates/trt-gst/src/lib.rs:312-316`

NvmmPreprocessStage::enqueue calls frame.cuda_import() (cudaImportExternalMemory + map) and Preprocessor creates/destroys a cudaTextureObject_t every frame (trt-preproc lib.rs:199-211, ~10 us acknowledged in the module doc). GStreamer decoders cycle a small fixed pool of DMA-BUF fds, so both are cacheable per fd — precisely what a VPI payload would hold.

**Recommendation:** Add an fd -> (CudaMemory, tex_obj) LRU cache inside NvmmPreprocessStage (invalidate on fd disappearance/caps change). This removes the only recurring per-frame setup cost on the zero-copy path.

#### [MINOR] Events exist only as internal timing markers; no public sync primitive, blocking multi-stream futures
`/home/nvidia/trt-rs/crates/trt/src/pipeline.rs:260-271`

CUDA events are recorded solely to measure gpu_ms inside Pipeline::next. There is no public Event type for cross-stream dependencies, which the single-shared-stream design currently avoids needing — but multi-camera pipelines, DLA-concurrent-with-GPU execution, and overlapping frame N+1 preprocessing with frame N inference (currently impossible: the design serializes everything on one stream with a full sync) all require stream/event composition. VPI treats events as a first-class concept for exactly this reason.

**Recommendation:** Promote Event to the public API (record/wait/elapsed) now while it is cheap, and let ExecCtx own a small stream set so a future scheduler can pipeline frames; keep the default at one stream + one sync.

#### [MINOR] Source trait carries no frame metadata (timestamp, sequence, camera id, dimensions)
`/home/nvidia/trt-rs/crates/trt/src/pipeline.rs:14-17`

Source yields a bare Frame; NvmmFrame has fd/pitch/size but no PTS or sequence number, and dimensions travel out-of-band via RtspSource::width()/height(). Detections/keypoints emerge with no association to capture time — fatal for tracking, multi-camera sync, and the owner's spatial-pipeline plans. The pad32/letterbox geometry also has no carrier, hence the manually-coupled LetterboxInfo (finding above).

**Recommendation:** Define FrameMeta {pts, seq, source_id, width, height, transform: Option<LetterboxInfo>} and flow it through ExecCtx or alongside the data type, so operator outputs are timestamped and coordinate-mappable for free.

#### [INFO] sm_87 and engine input names hardcoded; no DLA seam in Engine/Session
`/home/nvidia/trt-rs/crates/trt-preproc/src/lib.rs:134`

nvrtc arch is fixed to sm_87 (acceptable per CLAUDE.md's Jetson-only scope, but every kernel-bearing crate repeats the assumption), and input tensor names ('image', 'images') are string literals inside stages. DLA: Orin has 2 DLA cores; TRT engines can be built with DLA layers and a core is selected at runtime, but engine building is fully external (trtexec) and Session exposes no device/core config. DLA matters less for accuracy-critical custom models (layer support is narrow) and more for offloading steady-state models (e.g. YOLO) to free the GPU for new operators — relevant given 'more models coming'.

**Recommendation:** Query compute capability for nvrtc arch; resolve input names from engine.specs() (first/only input) instead of literals. For DLA, do not build an abstraction yet — just add an in-library engine builder (or trtexec wrapper) with device_type/DLA-core options and a Session field, keeping the door open for a Backend::Dla variant later.

#### [INFO] Ideal end-state: a new NN operator in ~20 lines via ModelSession + Operator trait
`/home/nvidia/trt-rs/crates/trt/src/pipeline.rs:29`

Today a new model needs: a Session, manual input-name binding, unsafe run_device_inputs_on_device, shape bookkeeping duplicated from the engine, an output()/panic pattern, and (if it has GPU postproc) hand-rolled kernel-source strings + launch code (compare XFeat's three near-identical Stage impls in model.rs:112-143, 190-218, 313-348 — the same model wrapped three ways). Target shape: struct DepthOp { sess: ModelSession, out: Tensor } impl Operator { type Input<'a> = &'a Tensor; type Output = Tensor; fn enqueue(&mut self, cx: &ExecCtx, img: &Tensor) -> Result<()> { self.sess.bind("image", img)?.enqueue(cx) } fn finalize(&mut self, cx: &ExecCtx) -> Result<&Tensor> { self.sess.output_into("depth", &mut self.out)?; Ok(&self.out) } } — engine path + one bind + named outputs, with shapes/dtypes flowing from the engine automatically and postproc kernels registered as a reusable KernelSet payload.

**Recommendation:** Build ModelSession (safe bind-by-name with shape checks from engine.specs(), typed output views) and a KernelSet helper (nvrtc JIT a set of named kernels once, arch auto-detected) as the two ingredients; then collapse XFeat's three Stage impls into one Operator as the proving ground.

## API Ergonomics (operator authoring)

Writing a new operator today costs ~110 lines of scaffolding (beyond the CUDA kernel and algorithm), of which ~75 lines are verbatim copies of XFeat/Preprocessor patterns, touching 6-7 unsafe blocks and ~13 distinct concepts. The big four taxes are: (1) three incompatible error shapes bridged by 10 `.map_err(|e| e.to_string())` calls because library constructors return non-Send Box<dyn Error>; (2) no kernel helper — nvrtc compile/load is duplicated per crate and pointer extraction appears 19 times in two different idioms with hand-rolled grid math; (3) the two-phase Option/take/expect state dance plus per-stage `unsafe impl Send`, hand-rolled four times and codified in the skill instead of abstracted; (4) TRTensorMap drops dtype/shape, forcing stringly lookups, unchecked f32 casts, and hardcoded h/8 strides. The Pipeline/Stage core itself (typed .pipe chaining, one sync per frame, CUDA-event timing) is sound and worth keeping — the gap is entirely in the operator-author surface. Four focused additions to the trt core crate (unified Error, Kernels/launch helper with auto arch, an Op trait with typed Pending wrapped by a Stage adapter, TensorView outputs) get a new GPU operator to ~30-40 lines with zero unsafe.

### Findings

#### [MAJOR] Three incompatible error shapes force .map_err(|e| e.to_string()) bridging in every operator
`crates/trt-xfeat/src/model.rs:103`

Operators juggle trt::error::Result<T> (TrtError, crates/trt/src/error.rs:17), pipeline BoxError (Send+Sync, pipeline.rs:9), and non-Send Box<dyn Error> returned by XFeatPostproc::new/process (postprocess.rs:242,308,386), Preprocessor::new (trt-preproc/src/lib.rs:132), and XFeatBuilder::build (model.rs:60). Because Box<dyn Error> is not Send+Sync, every call from a Stage must stringify: 10 occurrences of `.map_err(|e| e.to_string())` (model.rs:103,136,184,200,210,272,330,340; trt-preproc/src/lib.rs:261; trt-gst/src/lib.rs:313). This destroys error structure (everything becomes a String) and is mandatory ceremony in every new operator constructor and enqueue/finalize body (~6-8 lines per operator).

**Recommendation:** One error type: extend TrtError (rename trt::Error) with #[from] variants for cudarc::driver::DriverError, cudarc::nvrtc::CompileError, and a Msg(String) catch-all; make Stage::enqueue/finalize return Result<_, trt::Error> (or keep BoxError but make ALL library constructors/methods return Send+Sync errors so plain `?` works). Deletes all 10 map_err sites.

#### [MAJOR] No kernel-authoring helper: ~40 lines of nvrtc + CUdeviceptr + LaunchConfig boilerplate per GPU operator, in two inconsistent idioms
`crates/trt-xfeat/src/postprocess.rs:243-295`

The nvrtc compile/load block (CompileOptions{arch:"sm_87",include_paths}, compile_ptx_with_opts + map_err format, load_module, load_function per kernel) is duplicated verbatim in postprocess.rs:243-256 and trt-preproc/src/lib.rs:133-141 (~12 lines each). Pointer extraction for launches appears 19 times in TWO different idioms in the same file: `ptr as usize as CUdeviceptr` (postprocess.rs:274-275,347,402-403,455) vs `{ use cudarc::driver::DevicePtr; x.device_ptr(self.stream.as_ref()).0 }` inline blocks (postprocess.rs:404,456-457,475,509-513), plus the descs_raw re-acquisition oddity at 362/475. Every launch also hand-writes grid math `((w+bx-1)/bx, (h+by-1)/by, 1)` (postprocess.rs:280-284, trt-preproc/src/lib.rs:223-227) and scalar `as i32` shadow variables (postprocess.rs:285-287,351-353). Net: each new kernel costs ~20 lines of launch scaffolding and 1 unsafe block, and the developer must know the DevicePtr-trait-import quirk.

**Recommendation:** Add trt::cuda::Kernels in the core crate: `Kernels::compile(&stream, SRC)?` (arch auto-detected from device compute capability, not hardcoded sm_87) and `Kernel::launch_2d((w,h), (32,8), args!(...))?` where an Arg enum has From impls for &CudaSlice<T>, *const T/*mut T, i32/u32/f32/u64 — centralizing both pointer idioms, grid math, and the single unsafe. A launch becomes 2-4 safe lines.

#### [MAJOR] Two-phase state pattern is a per-operator footgun: Option fields + take().ok_or + expect() + unsafe impl Send, hand-rolled 4 times
`crates/trt-xfeat/src/model.rs:159-218`

Each two-phase stage manually carries `pending: Option<*const f32>` + `result: Option<Output>`, sets in enqueue, `take().ok_or("finalize called before enqueue")?` in finalize, and `self.result.as_ref().expect(...)` in output() — a runtime panic if the Pipeline contract is violated. Pattern duplicated in XFeat (model.rs:239-240,337,346), XFeatPostprocStage (164-165,207,216), XFeatInferStage (141), Preprocessor (_pending, trt-preproc/src/lib.rs:121,262-269). The raw-pointer field additionally forces a per-stage `unsafe impl Send` with safety comment (model.rs:169,244; trt-preproc/src/lib.rs:66) — the skill file (.claude/skills/writing-pipeline-stages/SKILL.md:28-30) documents this as a rule rather than fixing it. That's ~14 lines + 1 unsafe + 2 panic sites per operator.

**Recommendation:** Introduce `trait Op { type Input; type Output; type Pending: Send; fn enqueue(&mut self, &Input) -> Result<Pending>; fn finalize(&mut self, Pending) -> Result<Output>; }` with a blanket `impl Stage for OpAdapter<O>` that owns the Option dance and the expect exactly once in the framework. Pair with a `DevPtr<T>(*const T)` newtype (Send via one central unsafe impl) so operator structs never write unsafe. Keep Stage as the low-level escape hatch.

#### [MAJOR] TRTensorMap is stringly-typed raw pointers with no dtype/shape — forces hardcoded strides and unchecked casts in postproc stages
`crates/trt/src/pipeline.rs:74-83`

TRTensorMap(pub HashMap<String, *const c_void>) discards the dtype/shape metadata Session already has (session.rs:45-49, resolved_output_shape). Downstream stages do `input.get("descriptors").ok_or("no 'descriptors' output")? as *const f32` (model.rs:195-197) with no type check, and must hardcode geometry: XFeatPostprocStage takes h/w in its constructor and derives hd=h/8 (postprocess.rs:310-311) instead of reading the actual tensor shape — a silent-corruption risk if the engine changes. The triple ok_or+cast block is repeated 3 times in model.rs (129-131, 195-197, 297-299, 325-327).

**Recommendation:** Make the inter-stage currency `HashMap<String, TensorView>` where TensorView = { ptr, dtype: DType, shape: Vec<usize> } populated from Session metadata; add `map.f32("descriptors")? -> TensorView` that validates dtype and exposes shape, so postproc stages derive strides from the actual engine output instead of constructor params.

#### [MINOR] Constructor conventions inconsistent: new vs with_stream vs Builder mean different stream semantics; XFeat has three overlapping entry points
`crates/trt-xfeat/src/model.rs:48-110`

`new` sometimes means private stream (Session::new session.rs:124, XFeat::new/XFeatBuilder::build model.rs:60-70 — incompatible with Pipeline), sometimes shared stream (TrtInferStage::new pipeline.rs:99, YoloInferStage::new trt-yolo/src/lib.rs:322, Preprocessor::new, XFeatPostproc::new). XFeat alone has XFeatBuilder, XFeat::new, and XFeat::with_stream, plus the legacy XFeatInferStage (model.rs:85-143) which hides a stream sync inside enqueue — the exact anti-pattern the skill warns about. Stream accessors are also inconsistent: XFeat::stream() -> &trt::Stream (model.rs:279) vs XFeatInferStage::cuda_stream() -> Arc<CudaStream> (model.rs:107). App setup requires the 3-step Logger->Runtime->Engine ceremony plus the awkward `Stream::new_standalone()?.cuda_stream().clone()` (examples/rtsp_xfeat/src/main.rs:85-102).

**Recommendation:** Adopt one convention: every stage constructor takes a `&PipelineCtx` (owns runtime + shared Arc<CudaStream> + engine cache; `PipelineCtx::new()?` replaces Logger/Runtime/Stream ceremony). Delete XFeatInferStage and XFeat::new's private-stream path; keep exactly one constructor name per stage.

#### [MINOR] Internal duplication: Session::new vs with_stream (~30 lines) and XFeatPostproc::process vs launch_score_nms+process_topk_sample (~100 lines)
`crates/trt/src/session.rs:91-157`

Session::with_stream (session.rs:91-121) and Session::new (124-157) duplicate the per-tensor buffer-allocation loop verbatim. XFeatPostproc::process (postprocess.rs:379-486) re-implements everything in launch_score_nms (265-295) + process_topk_sample (302-371) including the top-K CPU selection, kernel launches, and the candidates sort — a bug fixed in one path will be missed in the other. This is also the template new operator authors copy, doubling perceived API surface.

**Recommendation:** Session::new = CudaContext::new + Stream::new + delegate to with_stream. XFeatPostproc::process = launch_score_nms + sync + process_topk_sample. Pure deletion, no behavior change.

#### [MINOR] sm_87 hardcoded in two crates blocks the stated VPI-like portability goal
`crates/trt-preproc/src/lib.rs:134`

CompileOptions{arch: Some("sm_87")} is hardcoded in trt-preproc/src/lib.rs:134 and trt-xfeat/src/postprocess.rs:244 (and prescribed by .claude/skills/rust-cuda-patterns/SKILL.md:29). Any future operator copies it. On Orin NX/Nano it happens to work, but Thor (sm_101) or non-Jetson targets silently get wrong arch.

**Recommendation:** Query compute capability once via cudarc device attributes inside the proposed Kernels::compile helper; remove the literal from operator crates and the skill.

#### [MINOR] Public API hygiene: dual Stream types, cross-crate re-export leak, mutable pointer from &self
`crates/trt/src/lib.rs:37-41`

lib.rs publicly exports both the trt::Stream wrapper and cudarc's CudaStream; users must hop `session.stream().cuda_stream().clone()` (pipeline.rs:113, model.rs:108) and Pipeline::next internally rewraps via Stream::from_cuda_stream (pipeline.rs:274). DeviceBuffer is exported though it is an internal detail (trt-yolo uses it at lib.rs:247, but operators should use TRTensor). trt-xfeat re-exports trt_preproc::{Preprocessor, TextureGuard} (trt-xfeat/src/lib.rs:12) — a layering leak; an operator crate should not be the distribution point for the preprocessor. TRTensor::as_mut_ptr(&self) -> *mut c_void (tensor.rs:58) hands out mutable device pointers from a shared reference, and Stage::enqueue receives &Input yet mutates the input tensor's memory through it (pipeline.rs:121-124) — works under stream ordering but the signature lies.

**Recommendation:** Pick Arc<CudaStream> as the single public stream currency (keep trt::Stream crate-private); drop the trt_preproc re-export from trt-xfeat; consider as_mut_ptr(&mut self) or a doc-noted DevPtr accessor; demote DeviceBuffer to doc(hidden) once TRTensor covers the yolo use.

#### [INFO] Measured cost of a new operator today: ~110 lines of scaffolding, ~75 verbatim-copied, 6-7 unsafe blocks, 13 distinct concepts
`crates/trt-xfeat/src/model.rs:159-218`

Dry run (monocular-depth TRT model + one GPU colormap kernel) modeled line-by-line on the XFeat/Preprocessor templates: nvrtc ctor ~19 lines, launch fn ~22, stage struct + Options ~10, unsafe impl Send 2, constructor ~14, Stage impl ~32, crate plumbing ~12 = ~110 lines excluding the CUDA source and actual algorithm. Concepts a newcomer must learn: nvrtc CompileOptions, module/function loading, two CUdeviceptr idioms, DevicePtr trait import, LaunchConfig grid math, PushKernelArg, unsafe alloc, unsafe impl Send, Option/take/expect two-phase, 3 error types + to_string bridging, with_stream semantics, stringly TRTensorMap, Stream/CudaStream duality. With the unified error type, Kernels/launch helper, Op trait adapter, and TensorView map, the same operator is ~30-40 lines with zero unsafe in operator code and 2 concepts (Op trait + Kernel::launch).

**Recommendation:** Treat 'new TRT-model operator in <40 lines, zero unsafe' as the acceptance test for the refactor; port XFeatPostprocStage and YoloInferStage to the new helpers as the proof.

Replace hand-rolled two-phase state with `trait Op { type Pending: Send; fn enqueue(..)->Result<Pending>; fn finalize(.., Pending)->Result<Output> }` plus a framework OpAdapter implementing Stage, and a DevPtr<T> Send newtype — eliminates per-operator Option fields, take/expect panics, and `unsafe impl Send`.
4. Upgrade TRTensorMap to typed TensorView entries (ptr + dtype + shape from Session metadata) with checked accessors like `.f32("depth")?` — removes ok_or+cast triples and hardcoded stride math (h/8) in postproc stages.
5. Standardize construction: a PipelineCtx (runtime + shared Arc<CudaStream>) passed to every stage constructor, replacing the Logger->Runtime->Engine->Stream::new_standalone ceremony and the new/with_stream/Builder ambiguity; delete the legacy XFeatInferStage and XFeat's private-stream path.
6. Cheap cleanups: dedup Session::new vs with_stream (~30 lines) and XFeatPostproc::process vs launch_score_nms+process_topk_sample (~100 lines); drop trt-xfeat's re-export of trt_preproc; make Arc<CudaStream> the only public stream type; then port YoloInferStage and XFeatPostprocStage to the new helpers and update the two skills to teach the helper path instead of the boilerplate.

## Shipping & Model Weights

The shipping story is currently pre-zero: the entire current codebase is untracked in git (the index still holds the deleted old layout), there is no remote, no LICENSE file, no CI, and the README describes a removed architecture. Weights hygiene is half-right — *.engine and *.onnx are gitignored — but the .gitignore misses .onnx.data/.pt/.jpg, and 25M of stray YOLO artifacts sit at the repo root. For distribution, the clear winner is Hugging Face Hub via the hf-hub crate with sha256-pinned ONNX files, because it matches the owner's existing kornia-rs convention (hf-hub 0.4.2 workspace dep, optional hub feature, SHA-256 verified on every load path in kornia-xfeat), supports per-file downloads on slow Jetson links, and scales to the planned 5-100MB models where git-lfs and in-repo storage do not. Engines must be built on-device into a versioned cache (~/.cache/trt-rs/engines/<name>-<onnx_sha8>-trt<ver>-sm<cc>.engine) via an nvonnxparser bridge behind the existing-but-empty `builder` feature, with trtexec as fallback. Publishing is blocked by three hard issues: the crate name `trt` is already taken on crates.io, trt-yolo depends on kornia crates via absolute /home/nvidia paths, and trt-sys has no docs.rs/offline story; trt-gst and nvbuf-sys should stay unpublished Jetson-only adapters.

### Findings

#### [CRITICAL] Git index does not contain the current codebase; no remote configured
`/home/nvidia/trt-rs (git status)`

git ls-files shows only the OLD layout (trt/, trt-sys/, trt-detector-node/ — all staged as deleted, uncommitted). The entire current tree (crates/, examples/, models/, scripts/, CLAUDE.md, .claude/) is untracked, and `git remote -v` is empty. Nothing shippable is committed or backed up anywhere; the last commit (fe194fc) predates the whole pipeline architecture.

**Recommendation:** Before any distribution decision matters: commit the restructure (the old-path deletions plus crates/, examples/, scripts/, docs), push to a GitHub remote. Do this only after fixing the .gitignore gaps below so `git add .` doesn't capture binaries.

#### [MAJOR] .gitignore gaps: *.onnx misses external-data files, *.pt and images not ignored
`/home/nvidia/trt-rs/.gitignore:5-8`

Patterns `*.engine` and `*.onnx` exist, but `models/xfeat/xfeat_backbone.onnx.data` (2.6M, ONNX external-data sidecar) does NOT match `*.onnx` and would be committed by `git add .` — without its companion .onnx, i.e. useless on its own. Also unignored: `yolo11n.pt` (5.6M, repo root) and `frame_000000.jpg` (787K, repo root). 25M of stray weights/engines sit at the repo root (yolo11n.onnx 10.7M, yolo11n.fp16.engine 8.8M, yolo11n.pt).

**Recommendation:** Ignore `models/` wholesale plus `*.onnx.data`, `*.pt`, and root-level debug images; delete or relocate the stray yolo11n.* files into the cache dir. Per the decision below, the repo should carry no weights except tiny fixtures (matching.onnx at 2K is an acceptable test fixture if moved under a tests/fixtures/ path that is explicitly un-ignored).

#### [CRITICAL] Crate name `trt` is already taken on crates.io
`/home/nvidia/trt-rs/crates/trt/Cargo.toml`

Verified via crates.io API: crate `trt` exists (26 published versions, last updated 2024-06-13, unrelated project). `trt-sys` is free, but publishing trt-sys under a name that pairs with someone else's `trt` crate is incoherent. The whole naming scheme (trt, trt-sys, trt-preproc, trt-xfeat, trt-yolo, trt-gst) is unpublishable as-is.

**Recommendation:** Pick a free namespace before writing any more public docs: e.g. `trtrs`/`trtrs-sys` or, given the kornia-rs affiliation and the VPI-like operator-library direction, `kornia-trt`/`kornia-trt-sys` (check availability for whichever is chosen). Rename early — it is much cheaper now than after README/blog exposure.

#### [CRITICAL] trt-yolo depends on kornia crates via absolute local filesystem paths
`/home/nvidia/trt-rs/crates/trt-yolo/Cargo.toml:8-9`

`kornia-image = { path = "/home/nvidia/kornia-rs/crates/kornia-image" }` and same for kornia-imgproc. The workspace does not build on any machine except this Jetson, blocks `cargo publish`, and blocks CI entirely.

**Recommendation:** Switch to published kornia-image/kornia-imgproc versions from crates.io (kornia-rs publishes them), or make them optional behind a feature if only used for letterbox helpers. This is a prerequisite for every other distribution step.

#### [MAJOR] DECISION — weights distribution: Hugging Face Hub + hf-hub crate, sha256-pinned ONNX; not git-lfs, not Releases, not in-repo
`/home/nvidia/trt-rs/models/xfeat/`

Current state: 9.9M of ONNX+engine in models/ (untracked, so removable at zero history cost — act before first commit). Evaluation: (a) git-lfs taxes every clone, has GitHub bandwidth quotas, and pulls all models even when a user wants one — bad for slow/metered Jetson links; (b) HF Hub + hf-hub crate gives per-file download, etag-based caching in ~/.cache/huggingface, revision pinning, and is the exact convention the owner already uses in kornia-rs (workspace dep hf-hub 0.4.2 at /home/nvidia/kornia-rs/Cargo.toml:42; optional feature `xfeat-hub = ["dep:hf-hub"]` at kornia-rs/crates/kornia-xfeat/Cargo.toml:53; SHA-256 pin verified on every load path at kornia-xfeat/src/weights.rs:108-117, const PACKED_WEIGHTS_SHA256); (c) GitHub Releases works but has no Rust-native client, clumsy per-file versioning, and ties weight versions to code tags; (d) ONNX-in-repo dies at the stated 5-100MB+ future models. Caveat hf-hub must handle: xfeat_backbone.onnx uses external data (xfeat_backbone.onnx.data) — both files must be fetched into the same directory.

**Recommendation:** Choose (b). Create one HF model repo (e.g. kornia/trt-rs-models or under the owner's account) holding onnx + sha256 manifest per model. Add a small `trt-hub` module (or crate) with a static registry: model name -> { hf repo, revision, files[], sha256[] }. Gate behind feature `hub = ["dep:hf-hub"]` exactly like kornia-xfeat, and always verify sha256 after download (slow connections corrupt; pins give reproducibility). Offline path: accept explicit file paths everywhere, hub is convenience only.

#### [MAJOR] DECISION — engine lifecycle: build on-device from ONNX into a versioned cache; engines never ship
`/home/nvidia/trt-rs/crates/trt/Cargo.toml:10`

Today the examples take a pre-built .engine path as argv[1] (examples/rtsp_xfeat/src/main.rs:79-87) and engines are built manually via scripts/trtexec.sh; models/xfeat/xfeat_backbone_fp16.engine (2.0M, machine-locked TRT 10.3.0.30+SM87) sits next to the ONNX, one `git add` mistake from being committed. The `builder = []` feature in crates/trt/Cargo.toml:10 is an empty stub — no nvonnxparser symbols exist in trt-sys/include/trt_bridge.h.

**Recommendation:** Implement the in-process builder as the primary path: add btrt_build_engine_from_onnx (createInferBuilder + nvonnxparser + buildSerializedNetwork, fp16 flag, opt-profile params) to the trt-sys C bridge behind the `builder` feature (links nvonnxparser, already on every JetPack install). Cache key: ~/.cache/trt-rs/engines/<model>-<sha256(onnx)[..8]>-trt<MAJOR.MINOR.PATCH.BUILD from existing build.rs env consts>-sm<cc>.engine, written atomically (tmp file + rename) so concurrent first-runs don't corrupt. Fall back to a trtexec subprocess (/usr/src/tensorrt/bin/trtexec) only when the feature is off. First-run UX: log 'building engine for xfeat (one-time, ~1-3 min)'. Repo contents: source + export scripts + tiny fixtures only; no .onnx, no .engine.

#### [MAJOR] trt-sys build.rs unconditionally requires TRT headers — docs.rs build will fail; env-override story is half done
`/home/nvidia/trt-rs/crates/trt-sys/build.rs:4-7`

Good: TRT_INCLUDE_DIR / TRT_LIB_DIR / CUDA_HOME overrides exist with rerun-if-env-changed, so x86 TRT installs can build. Bad: defaults are aarch64-only (/usr/include/aarch64-linux-gnu), cc + bindgen always run, so docs.rs (no TRT, x86) fails immediately. Also TRT version constants are hardcoded 10.3.0.30 in build.rs:58-61 rather than parsed from NvInferVersion.h, so an env-override build against TRT 10.9 silently lies about its version — which would poison the engine-cache key proposed above. nvbuf-sys/build.rs additionally hardcodes /usr/src/jetson_multimedia_api and /usr/lib/aarch64-linux-gnu/nvidia with no overrides at all.

**Recommendation:** In trt-sys build.rs: if env DOCS_RS is set, emit cargo:rustc-cfg=trt_stub and skip cc/bindgen, with a pre-generated bindings snapshot (or empty stub module) committed for that cfg; add [package.metadata.docs.rs] to set the cfg. Parse TRT version from $TRT_INCLUDE_DIR/NvInferVersion.h at build time instead of hardcoding. Mirror the env-override pattern in nvbuf-sys (JETSON_MULTIMEDIA_API_DIR, TEGRA_LIB_DIR). Keep trt-gst + nvbuf-sys Jetson-only: either publish = false initially, or publish with a loud platform note — they are inherently L4T-bound (nvbufsurface), feature-gating inside them buys nothing.

#### [MAJOR] Publish-blocking metadata gaps: missing LICENSE file, missing license/description in two crates, no repository field anywhere
`/home/nvidia/trt-rs/crates/trt-gst/Cargo.toml`

Workspace declares license = "Apache-2.0" but no LICENSE file exists in the repo (Apache-2.0 requires distributing the license text; kornia-rs has one). crates/trt-gst/Cargo.toml and crates/trt-yolo/Cargo.toml have neither license.workspace nor description — cargo publish rejects both. No crate has a `repository` field. Also trt-gst pins gstreamer 0.20 (current is 0.23.x) which will draw immediate version-bump pressure once public.

**Recommendation:** Add LICENSE (Apache-2.0 text) at root; add license.workspace, description, repository.workspace to every crate; decide gstreamer version before first publish.

#### [MINOR] No CI; README describes the deleted repo layout
`/home/nvidia/trt-rs/README.md:5-11`

README still documents the old three-crate layout including the removed trt-detector-node and bubbaloop integration. No .github/workflows. Realistic CI for this repo: clippy/fmt + the CPU-only unit tests (cargo test -p trt-yolo per CLAUDE.md) can run on GitHub x86 runners only if trt-sys gets the stub/docsrs cfg (or those crates are excluded); full builds need a self-hosted Jetson runner — which the owner has.

**Recommendation:** Rewrite README around the actual workspace; add two-tier CI: hosted runner doing fmt+clippy+CPU tests with TRT-dependent crates stubbed or skipped, plus a self-hosted Jetson job for cargo build --release of the examples and the engine-build smoke test.
